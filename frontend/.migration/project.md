## Behavior changes (flagged across all components — consolidated list)

- **tooltip.tsx**: enter/exit animation was silently BROKEN before this
  migration (no `tailwindcss-animate` plugin registered in
  `tailwind.config.ts`, so the old `animate-in`/`fade-in-0`/`zoom-in-95`
  classes were dead no-ops). The new `data-starting-style`/
  `data-ending-style` transition is a REAL, working fade+scale animation.
  Flagged as a visual behavior change (improvement), not silently patched.
- **sheet.tsx**: same root cause and same fix — the backdrop fade and
  per-side slide animation were dead no-ops before (no animate plugin);
  now they are real, working CSS transitions. Flagged as a visual behavior
  change (improvement).
- **sheet.tsx**: dropped a `data-[state=open]:bg-secondary` class on the
  Close button that was ALREADY DEAD in the radix version (Radix's
  `Dialog.Close` never set `data-state` on itself; only `Content`/`Overlay`
  did). No user-visible change since the class never fired on either side;
  documented as a dead-code removal, not a behavior change.
- No other behavior deltas identified. No consumer in this project
  exercises any of the documented Base UI defaults-differ-from-Radix cases
  (e.g. tooltip `sideOffset` was already 4 on both sides here; no
  `position="popper"`/accordion/menu/select usage exists in this project at
  all).

## Flagged for the supervising agent's decision (NOT fixed unilaterally)

**`components.json` style still reads as radix-oriented to the shadcn
CLI.** The project's style is `"default"` (legacy, unprefixed), which has
NO `base-default` counterpart in the shadcn registry (confirmed during
preflight). Per the runbook's "Legacy styles" rule, this migration used the
transformation engine directly on the project's own files rather than
retargeting `components.json` to a `base-<style>` value, because doing so
would have no registry target to point to and could misdirect future
tooling. Net effect: `components.json` was NOT modified by this migration
run, so it will still resolve to radix-style registry URLs if a future
`npx shadcn add <component>` (or `--overwrite`) is run — that command would
fetch and deliver a RADIX-based component into an otherwise now-fully-Base-UI
project, re-introducing the dependency this migration just removed.

Options for the supervising agent to choose from (none applied
unilaterally):

1. **Do nothing / accept the risk.** Since the project's style has no
   `base-default` counterpart, there may be no clean CLI-driven path
   forward anyway; future components would need the same hand-transform
   treatment this run used, regardless of what `components.json` says.
   Document the constraint (e.g. in this repo's contributor docs) so future
   `shadcn add` calls are done manually/reviewed rather than blindly
   trusted.
2. **Migrate the project's Tailwind/CSS-variable style to one of the
   PREFIXED styles that DOES have both a `radix-<style>` and
   `base-<style>` registry pair** (e.g. adopt `new-york`'s v4-prefixed
   successor, or whichever prefixed style the team prefers), then flip
   `components.json` to the `base-<style>` variant. This is a real
   visual/structural change to the design system, not a mechanical step,
   and should not be done without the team's sign-off since it would
   restyle the app.
  3. **Add a project-local note/lint step** that fails or warns if
   `npx shadcn add` is invoked, redirecting contributors to the migration
   runbook instead, without changing `components.json` itself.

This decision is left to the supervising agent / project owner; it was
explicitly out of scope to resolve unilaterally per the task instructions.
