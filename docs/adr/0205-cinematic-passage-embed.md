# ADR 0205: The blog card plays the cinematic replay

## Status

Accepted (2026-10-23). Fifth step toward a cinematic passage replay, after
[ADR 0200](0200-passage-replay-in-3d.md) (3D), [ADR 0202](0202-passage-replay-boat-model.md)
(the boat model) and [ADR 0203](0203-passage-replay-camera-shots.md) (camera
shots). Amends [ADR 0174](0174-passage-export-is-a-self-contained-card.md) and
[ADR 0199](0199-passage-map-satellite-imagery.md): the blog card is still always
the chart, never satellite photographs, but it is no longer flat. Signs are the
next step and are not in this one.

## Context

The in-app replay now has terrain, a model of the operator's boat and directed
camera shots. The blog card and the downloadable page still ran the player of
ADR 0174: a hand-written, dependency-free script of about 12 KB with its own
clock, its own fly-in and its own idea of where the boat is. Porting each new
replay feature into that script by hand would have meant two implementations of
the clock, the camera director and the heading rule, drifting apart one fix at a
time.

The card has constraints the app does not. It runs on a stranger's blog page,
with MapLibre already loaded there as a page global, and nothing in it may point
at the boat (ADR 0174). It is pasted into a Ghost HTML card, so it must be one
snippet of text.

## Decision

1. **One player, built from the app's own modules.** The card's player is
   TypeScript in `frontend/src/export-player/` and imports the same code the
   replay uses: the piecewise clock (`replay-clock`), the camera director and the
   hand-over gate (`replay-camera`), the pitched fit (`pitch-fit`), the heading and
   track index (`boat-model`), the boat geometry and layer, the terrain constants
   and the sailed-track helpers in `passages`. It imports no React, no
   react-map-gl and nothing that reaches the boat. A test checks the built text
   names none of them and carries no `/api/` address. `passage-export-player.js`
   is gone.

   It is built as a Vite library in IIFE form, with `maplibre-gl` and `three`
   marked external (neither is imported at run time: MapLibre arrives as the
   page's `window.maplibregl` and is handed to the player, and three.js is
   fetched, see 4). The built script is available to `passage-export.ts` through
   a virtual module, `virtual:passage-player`, from a small Vite plugin
   (`vite-plugin-passage-player.ts`) that runs the library build the first time
   the module is loaded and returns the text as a string. Two other ways were
   considered. A `?raw` import of a built file would need the build to have run
   before `npm run dev` and before vitest, and leaves a generated file to go
   stale. A TypeScript module generated by a build step has the same ordering
   problem plus a checked-in or ignored artefact. The virtual module works
   unchanged under `vite`, `vite build` and vitest, rebuilds when a file the
   player imports changes in dev, and leaves nothing on disk. The cost is a nested
   Vite build while the main one runs, a few hundred milliseconds.

   The nested build is always a production build: it defines
   `import.meta.env.DEV` false, `PROD` true, `MODE` production and
   `process.env.NODE_ENV`, so the card is the same text whether `vite`, `vite build`
   or vitest made it, and carries no dev-only debugging hook (a test checks the
   built text has no `__boatDebug`). A failed build is not cached: the next load
   tries again. The files the player imports are found by reading the imports,
   not from the build, so they are watched even when the build is broken. In dev a
   change to any of them clears the build and, through the `hotUpdate` hook,
   returns the virtual module with the changed ones, so `passage-export.ts`
   updates even when the changed file is outside the app's own module graph.

   The card script is `HcPlayer.initCard(id, window.maplibregl, document)`, run
   once per card inside its own function, so two cards on one page share nothing
   but the terrain protocol and the three.js load (see 3 and 4). Each press of Play
   starts a run with its own token: the fly-in's listener and timer belong to one
   run, are removed when the next starts, and cannot begin a newer run.
   A reader's browser without MapLibre gets the same error notice as before.

   To make that possible without dragging in the app, two shared modules changed.
   `boat-geometry` and `boat-layer` no longer import three.js or MapLibre's
   `MercatorCoordinate`: the caller hands them in (`createBoatLayer(hull, {
   three, MercatorCoordinate })`, `buildBoat(type, dims, three)`). The app imports
   three.js from its own lazy chunk and passes it; the card passes the CDN copy.
   The yield-and-resume logic that was inline in the map component is now
   `CameraGate` in `replay-camera`, used by both, with `sameCamera`.
2. **What goes into the card's data.** The export data gains `d3` (the 3D
   switch), `hull` (type, length overall and beam, or null), `shots` (the camera
   shots that fall inside an exported passage, oldest first, without ids) and,
   with 3D and a hull, the address and integrity hash of three.js. Nothing else
   is added: no signs, no track beyond the thinned track of ADR 0174. Without 3D
   the hull is dropped, so a flat card carries no vessel figures. The JSON still
   goes through `safeJson`.
3. **Terrain in the reader's browser.** The card fetches AWS Terrarium tiles
   directly (`https://s3.amazonaws.com/elevation-tiles-prod/terrarium/{z}/{x}/{y}.png`,
   maximum zoom 15) through a custom MapLibre protocol, `hcterrain-v1://`,
   registered with `addProtocol`. The name carries a version constant that is
   bumped whenever the clamp or the upstream address changes, and a page-level
   record makes each card register it only if no card has: two cards, or cards
   from two Helmcentral releases, on one page never replace each other's loader.
   The handler fetches the tile, sets every pixel below sea level to R=128 G=0
   B=0 (0 m) and hands MapLibre an `ImageBitmap` made from `ImageData`. The
   arithmetic is the boat proxy's (`backend/terrain_proxy.go`): Terrarium stores
   elevation as R*256 + G + B/256 - 32768, so a pixel whose 24-bit value is under
   128<<16 is below the sea. It lives in one pure function, `clampSeaPixels`,
   tested on pixel arrays with the Go cases.

   **The PNG is decoded by hand, not through a canvas.** Brave, Firefox with
   resist-fingerprinting and Safari's advanced tracking protection add noise to
   canvas readback, and one step in the red channel is 256 m, so a tile read
   through `getImageData` can raise the sea or sink a headland. `png.ts` parses the
   chunks, joins the IDAT data, inflates it with the browser's own
   `DecompressionStream('deflate')` (no dependency) and undoes the five row
   filters for 8-bit RGB and RGBA. Anything else (palette, 16-bit, interlaced) is
   refused loudly, since a Terrarium tile is none of them. Its tests decode real
   tiles fetched from AWS into `src/test/fixtures/terrarium` and compare the pixels
   with an independent decoder (Python's zlib and its own filter code), and
   exercise every filter type on written PNGs. MapLibre's own elevation path reads
   the `ImageBitmap` back itself; the card never does.

   The card uses exaggeration 1.5, the hillshade and the day sky of
   `lib/terrain.ts`: the card has no theme of its own, so it is always the day
   variant. The map stays on the globe projection of ADR 0174, so the opening
   still comes down from the whole earth; MapLibre cannot draw fog on a globe, so
   the horizon blend of ADR 0203 is weaker than in the app.

   A tile that cannot be fetched fails the source. The card shows "Terrain
   unavailable", takes the terrain, hillshade and sky off, puts the camera back
   level and carries on flat, with shots as zoom and centre only. If that happens
   during the fly-in, the fly-in is turned round to the flat framing and the replay
   begins from there. It does not retry and puts nothing in the tile's place.
4. **three.js with a pinned hash.** The boat model needs three.js, 690 KB, so the
   card loads it only when 3D is on and a hull type is set. It calls
   `fetch(url, { integrity })` for the jsDelivr ESM build of the exact version the
   app pins (0.170.0, `three.module.min.js`), so the browser refuses a body that
   does not match the sha384, then imports the checked text from a Blob URL. The
   hash was computed from `node_modules/three/build/three.module.min.js` and
   compared with the bytes jsDelivr serves for that URL (fetched with curl and
   hashed: identical). A test recomputes it from `node_modules`, as it does for
   MapLibre, so an upgrade cannot leave it stale. With the wrong hash the browser
   refuses the file, the card logs the failure and keeps the glowing dot (checked
   by hand). A blog whose content security policy forbids the fetch or Blob
   modules gets the dot the same way, and the console says once which directive
   to check (`connect-src cdn.jsdelivr.net`, `script-src blob:`); the same line is
   logged once for `connect-src s3.amazonaws.com` if terrain fetches fail like
   that. The load is kept on the page (`window.__hcpThree`, keyed by address and
   hash), so two 3D cards evaluate three.js once; a failed load is not kept, and
   the next card tries again. With no length overall the model is drawn at a fixed size on
   screen, as in the app, and the console says so once.
5. **Camera shots in the card.** The card plays the shots with the app's director
   and gate: ease into each shot from the live view; Overview, Follow and Orbit;
   orbit speed in degrees per second of watching; a pace slows the replay clock.
   The chosen play length (15, 30 or 60 seconds) is the length of the
   underway time at full pace, and the paces stretch it, exactly as in the app, by
   the same piecewise clock. Nights at anchor stay fixed pauses of the old length
   on top and are not paced. With no shots the plan is the old plan and the
   camera is left to the fly-in. Pitch and bearing are used only with 3D on and
   the terrain up. A mouse or pen drag past 4 px, a second finger, or Ctrl or
   Command with the wheel hands the camera to the reader until the next shot, or
   until Play or Resume is pressed; a tap does not. A single finger and the
   plain wheel are left to the page, which scrolls (the card keeps cooperative
   gestures). MapLibre's credit line is kept to its small icon (until the reader
   opens it) so the readout never sits on it. The pointer is read directly because the camera's own jump each
   frame swallows a drag's `movestart`. With reduced motion the camera cuts to
   each framing and again when the boat nears the edge, and the fly-in is a cut,
   as before.
6. **The Export menu.** A **3D** switch follows the passage map's 3D preference,
   the same way **Overview map in the corner** follows its own. Shots always go
   in; there is nothing to choose. They are read with the existing camera-shot
   query over the span of the exported passages. If that query fails, Copy and
   Download say so and stop, since an export without the shots the operator saved
   would be a different card with no word said. The still PNG exports are
   unchanged.
7. **What goes out.** Apart from the data above, the card now asks for two more
   public hosts at run time: `s3.amazonaws.com` for the elevation tiles and, with
   a hull type, `cdn.jsdelivr.net` for one more file. A blog that sets a content
   security policy needs to allow those hosts; the how-to lists the directives. The card still contains no
   address of the boat, and a test checks the full set of hosts in the snippet.
   The built player is about 27.8 KB (11.8 KB gzipped), up from 12.7 KB (4.1 KB).

## Rejected

- **Porting the new features into the old player by hand.** Quickest for one
  feature, and the reason the two players would drift: the clock, the heading
  rule, the director's easing and the pitched fit all have fixes still to come.
- **Hillshade only, with no raised terrain.** The same elevation tiles are
  fetched either way, but shading painted on a flat surface does not show the
  hills standing up, and a tilted Follow or Orbit shot over it looks wrong. Less
  faithful to what the operator saw in the app.
- **Proxying the elevation tiles or three.js through the boat.** The proxy
  already exists, but the card would then point at the boat, which ADR 0174 rules
  out, and a reader with no route to the boat would get no terrain.
- **Bundling three.js into the card.** It would put 690 KB in every pasted card,
  including those with no hull type or with 3D off.

## Consequences

- The card is larger, and readers on 3D cards make a few hundred requests to
  the AWS elevation bucket while it plays.
- A change to the replay's clock, director or heading rule reaches the blog card
  at the next export, without a second edit. The card already on a blog does not
  change (ADR 0174).
- Anything the player imports from the app must stay free of React and of
  app-only dependencies, or the build fails or the player grows. Tests catch the
  second by checking the built text.
- The card's data now carries a vessel's hull type and size. Nothing else about
  the boat goes out.
- Signs, with their photos inlined, are the last step and are not in the card yet.
