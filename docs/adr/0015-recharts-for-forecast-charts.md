# ADR 0015: Recharts (via shadcn) for the Forecast Panel's Hand-Rolled SVG Charts

## Status
Accepted

## Context

The Forecast panel's five hourly/day charts — Wind, Wave, Precipitation, Cloud & Temperature, and Tide (`forecast-drawer.tsx` and `tide-chart.tsx`) — were each a hand-rolled `<svg>`: manual `xFor`/`yFor` pixel-mapping functions, manual `<path>`/`<polyline>` series, manual per-tick `<text>`/`<line>` loops for axes and gridlines. Meanwhile every other data-shaped surface in this codebase already follows shadcn/ui conventions (`components.json`, generated `ui/*.tsx` primitives, Radix-based interactive components), and shadcn ships a first-class `chart` component built on Recharts. The forecast charts were the one place in the app that hadn't adopted that convention — not because Recharts was unsuitable, but because nobody had migrated them yet. This ADR is that migration.

The risk in migrating hand-rolled SVG to a charting library is usually a rewrite: recharts computes its own margins, its own axis scales, and ships its own tooltip — none of which naturally reproduce a bespoke pointer-tracking tooltip or bespoke shapes like wind barbs. The approach taken here was deliberately *not* a rewrite, for that reason.

## Decision

### Margin-matched drop-in, not a rewrite

Recharts' `<ComposedChart width={W} height={H} margin={{top, right, bottom, left}}>` always maps its plot rectangle to exactly `(margin.left, margin.top)`–`(W - margin.right, H - margin.bottom)`. Every existing hand-rolled chart already defined those same four numbers as constants (`hourlyChartLeft`/`hourlyChartRight`, and each chart's own `*ChartTop`/`*ChartBottom`). Passing those exact constants as recharts' `margin` makes recharts' internal pixel mapping identical to the existing manual `xFor`/`yFor` functions, with zero change to the numbers themselves.

That equivalence is why the existing `useChartTooltip` hook, `ChartTooltipBubble`/`ChartTooltipMarker` components, and hand-rolled shapes with no recharts equivalent (`WindBarb`, `WaveDirectionArrow`, the cloud-icon overlay row) needed no changes at all. They already computed pixel positions from the same constants; once recharts uses the same margins, those positions stay correct without modification. Each chart now renders as two layered siblings sharing one coordinate space: a `<ComposedChart>` for the parts recharts is good at (axis gridlines/tick labels, `<Area>`/`<Line>`/`<Bar>` series, `<ReferenceDot>`/`<ReferenceLine>` markers), and the original `<svg viewBox>` overlay — unchanged — for the tooltip hook, corner axis labels, and bespoke shapes. `WindBarb`'s and `WaveDirectionArrow`'s positioning moved from a plain per-tick loop into a recharts `<Customized>` layer, but the shapes themselves and the `hourlyXFor` calls that place them are untouched; `<Customized>` is just a way to render arbitrary children inside `<ComposedChart>`'s own coordinate space alongside its other layers, not a data-driven recharts primitive.

### Two margin-matching pitfalls that only showed up under real-browser pixel verification

The margin-matching guarantee above is only as good as recharts' *actual* rendered plot rectangle matching the margin box on every render, for every chart - and two distinct recharts behaviors silently violate that, neither of which `tsc`, `eslint`, or jsdom-based unit tests can catch, because none of them exercise real rendered SVG geometry. Both were found the same way: rendering the app in a real browser, tapping a chart to trigger the tooltip, and comparing the tooltip marker's (manually-positioned) pixel against the actual recharts-rendered curve's geometry at that same x (via `path.getPointAtLength`, scanning for the closest-x point) - a screenshot alone would not have shown either gap clearly enough to catch it.

**A visible `<XAxis>` reserves its own default `height` (30px) on top of the given `margin`.** Wind, Wave, Precipitation, and Cloud & Temperature each have one non-`hide`-den `<XAxis>` (the one rendering the 12AM/6AM/12PM/6PM tick labels). Recharts' offset calculation (`calculateOffset` in `generateCategoricalChart.js`) adds every axis's own `height`/`width` prop (default 30 for `XAxis`) to whatever `margin` a chart is given, *unless* that axis is `hide`-den - so the actual plot rectangle's bottom edge sat 30px higher than `margin.bottom` alone implied, compressing the real Y-scale relative to what every `*YFor` function (and therefore the tooltip marker) assumed. The fix is not `height={0}` - recharts' `CartesianAxis.render()` refuses to render any ticks at all when `height <= 0`, which was confirmed by trying it (broke every "shows 12AM/6AM/12PM/6PM" test). Instead, each affected chart's `margin.bottom` is now computed as `(chartSvgHeight - chartBottom) - RECHARTS_XAXIS_HEIGHT`, with `RECHARTS_XAXIS_HEIGHT = 30` explicitly also passed as that `XAxis`'s own `height` prop - so the *combined* reserved space (margin + axis height) still equals the originally-intended bottom band, and the axis keeps rendering its ticks normally.

**A `domain` array is silently widened to fit data that overflows it, unless `allowDataOverflow` is set.** This one is specific to Tide's identity-domain trick. `curvePoints` intentionally includes samples slightly outside `[0, viewportWidth]`/`[0, 175]` whenever a raised-cosine curve segment spans a day-window boundary (an extreme just before or after the visible window still needs to interpolate smoothly into it) - exactly as the original hand-rolled `<svg>` did, relying on the SVG viewport's own clipping to hide the overflow. Recharts' `parseSpecifiedDomain` (in `ChartUtils.js`), given an explicit numeric domain and `allowDataOverflow` at its default of `false`, computes `Math.max(specifiedDomain[1], dataDomain[1])` - i.e. it *widens* the domain to the data's actual extent rather than clipping the data to the given domain. Since the pixel *range* stays fixed at `[0, viewportWidth]` regardless, a wider domain compresses every plotted point's scale - and because the amount of overflow (and therefore the widened domain) depends on how far past the window edge the nearest extreme falls, the resulting gap between the recharts-rendered curve and the manually-positioned tooltip marker/`ReferenceDot`s *grew* across the chart rather than staying constant, which was the first clue this wasn't a simple offset bug. The fix is `allowDataOverflow` on both the `x` and `y` axis for Tide, telling recharts to trust the given domain literally and let genuinely out-of-range points overflow the plot (clipped by the chart's own SVG viewport, same as before). The same four hourly charts' `hourOfDay` axis got `allowDataOverflow` added defensively too, even though no failure was observed in practice: `hourOfDay` comes from a backend field that falls back to `-1` when malformed (`typeof entry.hour_of_day === 'number' ? entry.hour_of_day : -1`), which would trigger the identical domain-widening behavior on the low end of an otherwise-safe `[0, 23]` domain if that fallback were ever hit.

Both fixes are covered by regression tests that fail without them and pass with them (verified by temporarily reverting each fix, confirming the corresponding test failed, then restoring it): one parses a `<Line>`'s rendered `d` attribute directly and checks its first point against the same `*YFor` formula, and one adds tide extremes outside the window specifically to trigger the domain-widening path, then checks an in-window `ReferenceDot` is still pixel-exact.

### The app's own tooltip stays; recharts' `<Tooltip>` is never used

Recharts ships `<Tooltip>`/`ChartTooltip`/`ChartTooltipContent` (the latter generated into `ui/chart.tsx`), but this app's tooltip has behavior that diverges from recharts' default on purpose: pointer tracking via `pointermove`/`pointerdown` (not `mouseover`), and pointer-type-aware clearing — a mouse hides the tooltip on `pointerleave`, but touch does not, since `pointerleave` fires the instant a finger lifts and would otherwise make a quick tap flash the tooltip for one frame instead of showing it. That's load-bearing on a touchscreen helm dashboard, not a stylistic choice, so none of the five charts adopt recharts' tooltip — `ChartTooltip`/`ChartTooltipContent` are unused exports from `ui/chart.tsx` in this codebase, kept only because they came bundled with `ChartContainer`/`ChartConfig` from the same `shadcn add chart` command.

### `ChartContainer` is not used to wrap the rendered chart

`ui/chart.tsx`'s `ChartContainer` unconditionally wraps its children in `RechartsPrimitive.ResponsiveContainer`, which measures its own DOM node via `ResizeObserver`/`getBoundingClientRect` and clones the chart element with that measured width/height — overriding whatever `width`/`height` props the chart itself was given, with no way to opt out through `ChartContainer`'s public props. Two problems follow from that. First, in jsdom (this repo's test environment), `getBoundingClientRect` always returns 0, so any chart mounted through `ChartContainer` renders at 0×0 in every test — this app's own `useMeasuredWidth` hook already works around the identical jsdom gap by falling back to a fixed constant, rather than trying to make jsdom's measurement behave like a real layout engine, and this migration follows that existing precedent. Second, even in a real browser, `ResponsiveContainer`'s own measurement is a second, independent measurement from the one this app already computes (`forecastChartWidth` / `viewportWidth`, both derived via `useMeasuredWidth`) — and the margin-matching pixel-alignment guarantee this whole migration depends on requires recharts to render at *exactly* the same width the manual tooltip overlay's `viewBox` already assumes, not a width that merely tends to agree with it.

The resolution: each chart renders `<ComposedChart width={forecastChartWidth} height={175}>` (or the chart-specific height) directly, never nested inside `<ChartContainer>`, so recharts uses that explicit number unconditionally instead of measuring anything itself. `ChartConfig` (the type) is still imported from `ui/chart.tsx` and used — each chart defines a `ChartConfig` object mapping its data keys to the exact pre-existing hardcoded colors (e.g. `windSpeed: { color: 'rgba(37,99,235,0.95)' }`), and those colors are read directly into the `stroke`/`fill` props of the corresponding `<Area>`/`<Line>`/`<Bar>` — just not through a rendered `<ChartContainer>` wrapper, since that wrapper is precisely the thing that had to be bypassed.

One factual note: `npx shadcn@latest add chart` resolved `recharts@2.15.4` for this project (its React 18 setup), not v3 as assumed going in. That's a fact about what the shadcn CLI chose, not a decision this migration needed to make — the v2 API covers everything used here (`ComposedChart`, `Area`, `Line`, `Bar`, `Cell`, `XAxis`, `YAxis`, `CartesianGrid`, `ReferenceDot`, `ReferenceLine`, `Customized`).

### Tide's exception: a pixel-identity domain, not a data domain

The other four charts plot a real, uniformly-spaced hourly series, so handing recharts a real domain (`type="number" domain={[0, 23]}`, keyed on `hourOfDay`) and letting it compute the data-to-pixel mapping via the matched margin is a faithful 1:1 replacement for the manual math. Tide is structurally different: its curve comes from sparse tide extremes (a handful of highs/lows per day) run through a raised-cosine interpolation loop (`curvePoints`, `CURVE_STEPS` samples between each pair of extremes) that already produces literal SVG pixel coordinates, not real data values on a real domain — and that interpolation shape (a raised cosine specifically, not any of recharts' built-in spline `type`s like `monotone`/`natural`/`basis`) is what makes the tide curve look correct. Letting recharts interpolate would silently change the curve's shape, and there's no real "domain" to hand it in the first place — `curvePoints` already *is* the pixel mapping.

The fix kept the interpolation loop completely untouched and instead gave recharts an *identity* domain: `<ComposedChart width={viewportWidth} height={175} margin={{left: 0, right: 0, top: 0, bottom: 0}}>`, `<XAxis dataKey="x" type="number" domain={[0, viewportWidth]} hide />`, and `<YAxis dataKey="y" type="number" domain={[0, 175]} reversed hide />`. With zero margin, recharts' plot rectangle spans the entire `viewportWidth × 175` canvas. With the X domain set to exactly `[0, viewportWidth]` (the same range as the plot rectangle), a data point's `x` value maps to that same literal pixel — no rescaling. Y needed the extra `reversed` flag: recharts' un-reversed Y axis treats the domain *maximum* as "up" (screen pixel 0) and the minimum as "down," the opposite of what a plain top-down SVG pixel coordinate means (where a *smaller* `y` is higher on screen) — `reversed` flips that so domain value `0` maps to screen pixel `0` (top) and domain value `175` maps to screen pixel `175` (bottom), i.e. also an identity mapping. The net effect: a `curvePoints` entry `{x, y}` (already computed by the untouched `xFor`/`yFor` functions) renders at the literal SVG pixel `(x, y)`, and `<ReferenceDot x={xFor(t)} y={yFor(h)}>` for each tide extreme and the "Now" marker land at that same literal pixel too — so recharts' `<Area>`/`<Line>` curve and the manually-positioned `<ReferenceDot>`s stay pixel-aligned on top of it.

This was verified two ways, not just assumed. A new test (`tide-chart.test.tsx`, "places a high-tide ReferenceDot at its exact precomputed pixel position") renders a chart with a known extreme, independently recomputes the expected pixel via the same `xFor`/`yFor` formula, and asserts the actual rendered `<circle>` inside `.recharts-reference-dot` has that literal `cx`/`cy` — this failed before the migration (no such element existed) and passes after. Separately, a live-browser screenshot of the real Tide card confirmed each extreme's dot sits exactly on the recharts-rendered curve, and the "Now" marker's dot (computed via the same `yFor` as the curve, at the current time's `xFor`) sits precisely on the curve too rather than floating above or below it — the sanity check a matched-domain claim like this deserves.

`<ReferenceLine>` needed its `segment={[{x, y}, {x, y}]}` form rather than its default (a full-width/full-height line) for both the "Now" marker's vertical dashed line and the zero-height baseline, since both are only drawn between `CHART_TOP` and `CHART_BOTTOM` (or `CHART_LEFT`/`CHART_RIGHT`), not across the whole 175px canvas — `segment` draws exactly the same partial line the manual `<line x1 y1 x2 y2>` did.

### Tide's day-tick axis stayed manual, unlike the other four charts

The other four charts moved their 6-hour-block tick loop to a real `<XAxis dataKey="hourOfDay" ticks={[0,6,12,18]}>`, because `hourOfDay` is real data on a real domain. Tide's `dayTicks` (0/6/12/18/24h offsets from the window start) have no equivalent real domain to attach to — the chart's actual `XAxis` domain is `[0, viewportWidth]` in raw pixels, purely an implementation detail of the identity-domain trick above, not something a user-facing tick would mean anything on. Rendering visible ticks off that axis would mean either exposing meaningless pixel-domain tick values or fighting `tickFormatter` to reverse-derive a time from a pixel — more indirection than just keeping `dayTicks` as manual overlay `<text>`/`<line>` children, which is what this migration did, consistent with how corner axis labels and the min/max readouts on every other chart also stayed manual overlay children rather than being forced through a recharts axis that doesn't naturally fit them.

## Addendum (post-migration follow-up): Tide's identity-domain trick was replaced

The "Tide's exception" and "Tide's day-tick axis stayed manual" sections above describe the pixel-identity-domain design as originally shipped. That design has since been replaced: `tide-chart.tsx`'s `curvePoints` now stores real values (`{t: number /* ms epoch */, h: number /* display-unit height */}`) instead of pre-converted pixels, and recharts is given the chart's *real* domain (`<XAxis dataKey="t" type="number" domain={[chartStartMs, chartEndMs]} hide />`, `<YAxis dataKey="h" type="number" domain={[yMin, yMax]} hide />`) with a real margin (`{left: CHART_LEFT, right: CHART_RIGHT_MARGIN, top: CHART_TOP, bottom: 175 - CHART_BOTTOM}`) — the same margin-matched pattern already used by Wind/Wave/Precipitation/Cloud, rather than the zero-margin identity mapping. `ReferenceDot`/`ReferenceLine` now take real `x`/`y` values (time/height) instead of pre-computed pixels; the Y axis no longer needs `reversed` (a real value-based Y axis already puts larger values higher on screen, same as the other four charts), and the tooltip's former "reverse `xFor` to recover timeMs from a pixel" hack was deleted as a genuine simplification, since `curvePoints[idx].t`/`.h` already are the real time/height. `xFor`/`yFor` themselves are unchanged and still used, just no longer fed into recharts — only by the manual overlay `<svg>` (tooltip marker, corner labels, day-ticks, extreme labels) and to compute the `ReferenceDot`/`ReferenceLine` values from real data.

One part of the original identity-domain design did *not* disappear: `allowDataOverflow` is still required, now on the `t`/X axis only (empirically confirmed — see `tide-chart.tsx`'s inline comment at the `<XAxis>`). The interpolation loop's segment-skip guard (`if (tB < chartStartMs || tA > chartEndMs) continue`) only skips a whole segment when *both* its endpoints are outside the window on the same side; it does not stop a segment straddling the boundary (one extreme just outside the window, one just inside) from producing individual interpolated samples whose `t` genuinely falls outside `[chartStartMs, chartEndMs]`, for a smooth day-boundary curve — the same root cause `allowDataOverflow` was originally added for, just expressed in real time units instead of pixel units. Without it, the existing "keeps an in-window ReferenceDot pixel-accurate..." regression test fails hard (off by 30–500px, not a rounding fluke). The Y/`h` axis, by contrast, does *not* need `allowDataOverflow`: a segment's interpolated `h` values are mathematically bounded within `[min(hA, hB), max(hA, hB)]` by the raised-cosine formula, so they never leave `[yMin, yMax]` the way `t` can leave `[chartStartMs, chartEndMs]`.

Tide's day-tick axis remains a manual overlay, unchanged by this addendum — that decision (and its rationale) still holds.

This was verified the same two ways as the original migration: the existing pixel-position regression tests continue to pass unchanged (they already asserted the right contract — external `xFor`/`yFor` vs. the actual rendered pixel — independent of the identity-domain implementation detail), plus a new test asserting the curve still renders a continuous, non-degenerate set of points when extremes span both before and after the window. A live-browser `getPointAtLength` pixel-alignment pass (same method as originally used for this migration) confirmed sub-0.01px alignment between the tooltip marker and the rendered curve across multiple tap positions.

## Addendum (second follow-up): the charts were restyled, because a faithful migration preserved a hand-rolled look

The migration above was deliberately *not* a rewrite — it kept every pixel-math constant, every colour, and every curve shape exactly as the hand-rolled `<svg>` had them, so that the tooltip hook, wind barbs and wave arrows needed no changes. That was the right call for a migration, but it had a consequence this ADR did not anticipate: moving the rendering layer to recharts changed nothing about how the charts *looked*, so they went on looking hand-rolled. The specific tells were straight-segment polylines between hourly points, flat single-alpha area fills, `CartesianGrid` on exactly one chart out of five, legends that stood in for line swatches with an em-dash and two hyphens (`— Wind · - - Gusts`), and — most consequentially — series colours written as literal `rgba()`, which meant none of them responded to the dark-mode class the rest of the app themes through.

Six changes address that, none of which touch the library, the data, or the coordinate contract.

**Curves are `monotone`, except Tide.** All ten forecast series moved from `type="linear"` to `type="monotone"`. Tide's two series keep `type="linear"`, for the reason given in "Tide's exception" above and unchanged by the addendum that replaced the identity domain: `curvePoints` is a raised-cosine interpolation computed in app code, and the smoothness is already in the sampled data. Handing those samples to a recharts spline would interpolate an interpolation and distort a curve whose shape is physically meaningful. The distinction is now pinned by a test rather than left to a comment — d3-shape's monotone interpolator emits cubic `C` commands in the rendered `d` where `linear` emits only `M`/`L`, so asserting on the presence of a `C` distinguishes the two without depending on recharts internals.

**Series colours are theme tokens.** `--chart-wind`, `--chart-gust`, `--chart-wave`, `--chart-swell`, `--chart-temp` and `--chart-grid` are defined as bare HSL triplets in both `:root` and `.dark` in `index.css`, following the existing `--gauge-primary`/`--gauge-secondary` convention, and consumed as `hsl(var(--chart-*) / <alpha>)` with each call site's original alpha preserved. This brings the charts into line with AGENTS.md's prohibition on raw arbitrary colour values, and is what makes dark mode work at all.

That approach rests on a fact worth recording, because it is not obvious and the whole token scheme depends on it: **`var()` substitution works inside SVG presentation attributes** (`stroke=`, `fill=`), not only in CSS property declarations. Presentation attributes are parsed against the CSS value grammar, so `stroke="hsl(var(--chart-wind) / 0.95)"` resolves. This was verified directly in Chromium rather than assumed — both the plain and the slash-alpha form — before any colour was converted. The file already depended on this quietly via `AXIS_LABEL_COLOR = 'hsl(var(--muted-foreground))'`; had it not held, that axis-label colour would have been silently falling back to black this whole time. A CSS class would also work (and outranks a presentation attribute in the cascade) but was unnecessary.

**Two colour scales are deliberately left literal.** `UV_GRADIENT_STOPS` encodes the WHO UV Index bands and `precipBarColor()` encodes Apple Weather's Light/Moderate/Heavy mm/hr bands. These are published external scales whose specific colours carry the meaning — a reader recognises "purple means extreme UV" independently of this app's palette. Theming them would make them prettier and wrong. The rule this sets: tokenise colours that express *series identity*, leave colours that express *a standard's semantics*.

**Area fills are vertical gradients** on Wind, Wave and Temperature, fading from a visible tint at the curve to near-transparent at the baseline, built with `<defs>` + `useId()` per the pattern `depth-sparkline.tsx` established and the UV gradient in this file already followed. **Gridlines are consistent** — faint horizontal rules on all five charts, replacing the single `vertical` grid on Cloud & Temperature, since horizontal rules at the Y ticks are the convention for time-series weather charts and vertical hour dividers competed with the existing day-tick overlay. **Legends draw real swatches**, a small `<svg><line>` carrying each series' actual stroke, width and dasharray, via one local `LegendSwatch` component; the fake swatches had also drifted from the real `strokeDasharray` values they stood for.

**Units moved from the topmost tick label into each chart's header** ("Wind" → "Wind (kts)"). Tick labels render at `x={6}` while the plot rectangle begins at `hourlyChartLeft = 30`, so there was already a gutter and most labels sat in it comfortably; only the maximum tick overran, because that one alone appended the unit. Widening the gutter would have been the obvious fix and was rejected: `hourlyChartLeft` and `CHART_LEFT` are load-bearing pixel-math constants reproduced by hand in three separate test files, so moving them costs far more than moving a unit string.

### What this did to the tests

The margin contract and `allowDataOverflow` are untouched, and **no pixel-exactness assertion changed value**. But several of those tests locate the element they then measure *by its literal colour string* — `curves.find((path) => path.getAttribute('stroke') === 'rgba(37,99,235,0.95)')`, and a `path.recharts-curve[stroke="..."]` selector feeding the wind pixel assertion. Tokenising the colours necessarily changed those selectors, which is worth flagging as a general property of this suite rather than an incident: colour is currently load-bearing as a *test selector*, so any future palette change forces test edits that look alarming but are mechanical. In jsdom the attribute value stays the literal string `hsl(var(--chart-wind) / 0.95)` — CSS variables never resolve there — so selecting on the token text works exactly as selecting on the rgba text did. A `data-series` attribute per series would decouple this properly; that is not done here.

Verified with the full suite green (568 tests), a clean strict-`tsc` build, and a real-browser pass in **both** themes — the dark case being the one that could not previously have been correct, since a hardcoded `rgba()` has no way to respond to the `.dark` class. Cost is +560 bytes gzipped.

## Addendum (third follow-up): Merged Precipitation & UV Background into Cloud & Temperature Chart

To improve glanceability and reduce vertical layout clutter in the daily forecast panel, the standalone **Precipitation** chart was merged into the **Cloud & Temperature** chart, reducing the daily weather chart stack from 4 cards down to 3 (Cloud/Temp/Rain, Wind, Wave + Tide section).

Key changes:
- **Precipitation Bars**: Hourly rain intensity is rendered as vertical column bars (`<Bar dataKey="precipIntensityMm">`) plotted against the right Y-axis. Bar opacity and saturation scale continuously with precipitation probability (faint translucent light-blue for low probability up to deep royal blue for high probability).
- **UV Background Area**: UV index is rendered as a soft yellow/amber background gradient fill (`<Area dataKey="uvIndex" fill="url(#uv-gradient)">`) rather than an overlapping foreground line, avoiding visual collision with the temperature curve and rain bars.
- **Combined Tooltip & Legend**: Scrubber tooltips display temperature, condition, precipitation rate/probability, and UV index simultaneously. The legend reflects Temperature line, Rain probability bar, and UV background.

## Consequences

Positive:
- All four forecast charts now render their data series (bars/areas/lines), axis gridlines, and reference markers through recharts, adopting the same shadcn convention the rest of the app already follows, while the pointer-tracking tooltip, wind barbs, wave-direction arrows, and cloud-icon overlay — none of which have a recharts equivalent, or in the tooltip's case an equivalent whose behavior this app actually wants — are completely unchanged.
- The margin-matching strategy meant zero changes to any existing pixel-math constant (`hourlyChartLeft`/`*ChartTop`/`*ChartBottom`/`xFor`/`yFor`), and zero changes to `useChartTooltip`, `ChartTooltipBubble`/`ChartTooltipMarker`, `WindBarb`, or `WaveDirectionArrow`.
- Test coverage grew alongside the migration (test-first per chart): new assertions pin the recharts-specific rendering details most at risk of silently regressing — per-bar intensity-band coloring surviving the `<Cell>` boundary, the UV line's gradient `stroke` surviving the `<Line>` boundary, solid-vs-dashed line styling per series, and (for Tide) the exact pixel placement the identity-domain trick depends on.

Negative / explicitly deferred:
- `ChartContainer` — the one piece of `ui/chart.tsx` shadcn's `chart` add command is built around — ends up unused as a rendered wrapper across all five charts, for the `ResponsiveContainer`-measurement reasons above. Only its `ChartConfig` type is used. This is a deliberate, scoped exception specific to this app's fixed-coordinate/jsdom-testability requirements, not a statement that `ChartContainer` is broken or shouldn't be used elsewhere.
- `recharts` landed at v2.15.4, already flagged upstream as no longer actively developed in favor of v3. Revisiting that bump (and re-verifying the `ChartContainer` bypass and the Tide identity-domain trick still hold under v3's API) is future work, not part of this change.
- The Tide chart's day-tick axis is the one axis across all five charts that stayed fully manual rather than moving to a recharts `<XAxis>`, an intentional asymmetry with the other four documented above rather than an oversight.
